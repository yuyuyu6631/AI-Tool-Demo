# 公网部署与上线排障经验

记录 2026-04-29 这次 `/xingdp` 公网入口修复、重新部署和验收中踩到的问题。后续上线如果遇到“本地正常、外网异常”，先按这份清单排查。

## 当前公网形态

- 公网入口：`http://changsha.01view.ydns.eu:12318/xingdp/`
- 当前推荐部署模式：Web 使用 `NEXT_PUBLIC_BASE_PATH=/xingdp` 构建，Nginx 转发 Web 时保留 `/xingdp` 前缀
- API 通过 `/xingdp/api/` 入口转发到后端 `/api/`
- 浏览器可见的静态资源必须带 `/xingdp` 前缀，例如 `/xingdp/_next/static/...`
- 浏览器侧 API 建议走同源 `/xingdp/api/...`，避免暴露或依赖内网 IP

## 关键结论

### 1. `/xingdp` 子路径部署要保持 Web 和 Nginx 模式一致

当前推荐模式是：

- `NEXT_PUBLIC_BASE_PATH=/xingdp`
- `NEXT_PUBLIC_PUBLIC_BASE_PATH=/xingdp`
- `NEXT_PUBLIC_API_BASE_PATH=/xingdp`
- Nginx 的 `/xingdp/` 转发到 Web 时保留 `/xingdp/`
- Nginx 的 `/xingdp/api/` 转发到 API 的 `/api/`

如果沿用旧的“剥离 `/xingdp` 再转发给 Next”模式，则不要同时启用 Next `basePath`。两种模式不能混用，否则页面、RSC 或静态资源容易 404。

### 2. 站内链接必须统一生成 `/xingdp/...`

典型症状：

- 点击详情页后请求 `/tools/xxx` 而不是 `/xingdp/tools/xxx`
- 登录、场景、对比、分页请求落到根路径，公网返回 404
- DevTools Network 里出现大量 `?_rsc=...` 的 404

处理方式：

- 使用 `apps/web/src/app/lib/public-path.ts` 的 `withPublicPath()`
- `/tools`、`/tools/[slug]`、`/auth`、`/scenarios`、`/compare`、`/admin` 等浏览器可见链接都应经由该 helper
- 面包屑、页脚、Header、移动菜单、命令面板、详情页相关链接也要覆盖

### 3. public 静态资源也要补 `/xingdp`

典型症状：

- logo 丢失
- 工具 logo、详情媒体、favicon 请求 404

处理方式：

- `/brand/logo.png` 应输出为 `/xingdp/brand/logo.png`
- `/logos/...` 应输出为 `/xingdp/logos/...`
- 详情页媒体如果是站内相对路径，也要走 `withPublicPath()`
- 对 logo 这种 public 图片，如果使用 `next/image` 且已有反代前缀，必要时设置 `unoptimized`，避免图片优化器请求 `/_next/image?...` 掉到根路径

### 4. `/xingdp` 无尾斜杠有 nginx 重定向坑

这次线上确认：

```text
GET /xingdp?_rsc=...
301 Location: http://changsha.01view.ydns.eu:18080/xingdp/?_rsc=...
```

这是公网 nginx 的重定向配置问题，不是前端业务代码问题。前端已规避：

- 首页链接使用 `/xingdp/`
- 提交锚点使用 `/xingdp/#submit-tool`
- 容易触发根路径 RSC 预取的首页链接改为普通 `<a>`
- 详情页分类筛选改为 `/xingdp/tools?category=...`，不要回到 `/xingdp?category=...`

后续如果能改 nginx，建议把 `/xingdp` 统一 301 到 `/xingdp/`，并保留当前公网端口 `12318`，不要生成 `18080`。

## 部署步骤

### AI 服务配置

生产环境默认使用本机 Xinference：

```env
AI_PROVIDER=openai
AI_OPENAI_BASE_URL=http://host.docker.internal:9997/v1
```

API 容器通过 `host.docker.internal:host-gateway` 访问宿主机。如果 Xinference 跑在其它容器或机器上，应把 `AI_OPENAI_BASE_URL` 改成对应的 `/v1` 地址，不再使用 `edgefn.net`。

### 1. 本地验证

先跑常规测试：

```bash
npm run test:web
```

再用公网子路径跑生产构建：

```powershell
$env:NEXT_PUBLIC_BASE_PATH='/xingdp'
$env:NEXT_PUBLIC_PUBLIC_BASE_PATH='/xingdp'
$env:NEXT_PUBLIC_API_BASE_PATH='/xingdp'
npm run build:web
Remove-Item Env:\NEXT_PUBLIC_BASE_PATH
Remove-Item Env:\NEXT_PUBLIC_PUBLIC_BASE_PATH
Remove-Item Env:\NEXT_PUBLIC_API_BASE_PATH
```

### 2. 打包上传

部署包只包含前端、contracts 和根依赖文件，排除本地构建产物：

```powershell
tar --exclude='apps/web/node_modules' `
  --exclude='apps/web/.next' `
  --exclude='apps/web/.next-dev' `
  --exclude='apps/web/test-results' `
  --exclude='apps/web/playwright-report' `
  -cf tmp/xdp-deploy.tar `
  package.json package-lock.json deploy.sh scripts/install_git_hooks.js apps/web apps/api packages/contracts infra
```

远程目录：

```text
/home/agent/xingdianping
```

### 3. 远程构建参数

远程 `Containerfile.web.prod` 需要支持：

```dockerfile
ARG NEXT_PUBLIC_API_BASE_URL
ARG NEXT_PUBLIC_BASE_PATH
ARG NEXT_PUBLIC_PUBLIC_BASE_PATH
ARG NEXT_PUBLIC_API_BASE_PATH
ENV NEXT_PUBLIC_API_BASE_URL=${NEXT_PUBLIC_API_BASE_URL}
ENV NEXT_PUBLIC_BASE_PATH=${NEXT_PUBLIC_BASE_PATH}
ENV NEXT_PUBLIC_PUBLIC_BASE_PATH=${NEXT_PUBLIC_PUBLIC_BASE_PATH}
ENV NEXT_PUBLIC_API_BASE_PATH=${NEXT_PUBLIC_API_BASE_PATH}
```

构建命令：

```bash
podman build \
  --build-arg SERVER_API_BASE_URL=http://xdp-api:8000 \
  --build-arg NEXT_PUBLIC_BASE_PATH=/xingdp \
  --build-arg NEXT_PUBLIC_PUBLIC_BASE_PATH=/xingdp \
  --build-arg NEXT_PUBLIC_API_BASE_PATH=/xingdp \
  -t xdp-web:latest \
  -f Containerfile.web.prod .
```

如果必须彻底清缓存才加 `--no-cache`。平时不要无脑 `--no-cache`，会留下大量中间镜像层。

### 4. 重启 web 容器

只重启 web，不动 API、MySQL、Redis：

```bash
podman rm -f xdp-web || true
podman run -d --replace \
  --name xdp-web \
  --network xdp-net \
  --env-file /home/agent/xingdianping/.env.runtime \
  -p 3000:3000 \
  xdp-web:latest
```

确认容器：

```bash
podman ps --format '{{.Names}} {{.Status}} {{.Ports}}' | grep xdp-web
```

## Podman 磁盘问题

这次二次构建遇到：

```text
no space left on device
```

系统盘 `df -h` 看起来可能还有空间，但 rootless Podman 存储里中间镜像层可能已经满。先看占用：

```bash
df -h / /home || true
podman system df || true
podman images --format "{{.Repository}} {{.Tag}} {{.ID}} {{.Size}}" | head -30
```

如果确认主要是 `<none>` 悬空镜像，可清理：

```bash
podman image prune -f
```

注意：这会删除未被当前容器使用的悬空镜像/构建层，不会删除正在运行的容器。执行前应确认 `xdp-web`、`xdp-api`、MySQL、Redis 都在运行。

## 公网验收清单

### HTTP 验收

至少检查：

```text
GET http://changsha.01view.ydns.eu:12318/xingdp/
GET http://changsha.01view.ydns.eu:12318/xingdp/tools?page=2&page_size=24
GET http://changsha.01view.ydns.eu:12318/xingdp/tools/prezi
GET http://changsha.01view.ydns.eu:12318/xingdp/api/tools/search-index
GET http://changsha.01view.ydns.eu:12318/xingdp/brand/logo.png
```

期望：

- 页面返回 `200 text/html`
- API 返回 `200 application/json`
- logo 返回 `200 image/png`
- HTML 中不应包含 `192.168.8.113` 或 `192.168.8.200:8000`
- HTML 中应包含 `/xingdp/_next/static/`

### 浏览器验收

用 Playwright 或浏览器手工检查：

- `/xingdp/tools?page=2&page_size=24` 展示“工具目录”和“当前页：2”
- 点击第一张工具卡“查看详情”，URL 应为 `/xingdp/tools/...`
- 详情页可以显示标题、评测结论、访问官网、相关工具
- logo 的 `naturalWidth > 0`
- Network 不应出现业务相关 404
- 若出现 `net::ERR_ABORTED` 的 RSC 请求，先判断是否是正常导航中断，不要误判为页面错误

### 导购助手浮层验收

这次最后修复的是浮层首屏：

- 初始状态只保留两个核心提示卡：找工具组合、做同类对比
- 初始状态不展示底部快捷问题按钮，避免挤压内容
- 初始状态中间区域不启用内部滚动条
- 进入真实对话后消息区仍允许滚动
- 在窄视口 `520x420` 下，两个提示卡应完整可见，右侧不应出现突兀的内部滚动条

## 常见问题到修复路径

| 现象 | 优先检查 |
| --- | --- |
| 外网请求内网 IP | `api-base.ts` 和 `NEXT_PUBLIC_API_BASE_URL` 是否让浏览器直连内网 |
| 页面无样式 | `_next/static` 是否带 `/xingdp`，`NEXT_PUBLIC_ASSET_PREFIX` 是否生效 |
| `/tools` 可点但详情 404 | 站内 Link 是否没有走 `withPublicPath()` |
| logo 丢失 | public 图片路径是否带 `/xingdp`，是否被 `next/image` 优化器改到 `/_next/image` |
| DevTools 里大量 RSC 404 | Link 预取路径是否掉到根路径或 `/xingdp` 无尾斜杠 |
| RSC 请求到 `:18080` | nginx 对 `/xingdp` 无尾斜杠的 301 配置问题，前端用 `/xingdp/` 规避 |
| 远程构建失败 no space | `podman system df`，必要时 `podman image prune -f` |
