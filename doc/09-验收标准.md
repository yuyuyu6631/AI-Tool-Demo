# 验收标准

## 一、总体要求

- 当前验收以真实代码现状为准
- 前端、后端、测试与文档口径必须一致
- 任何“历史 Demo 路由”或“旧阶段范围”不能作为当前验收依据
- 对产品方向类文档，必须区分“当前已实现”和“规划中能力”

## 二、前端验收标准

| 编号 | 项目 | 验收说明 |
| --- | --- | --- |
| F-1 | 项目可启动 | 根目录执行 `npm run dev` 或 `python start.py` 后，首页可访问 |
| F-2 | 主路由可访问 | `/`、`/tools/[slug]`、`/scenarios`、`/scenarios/[slug]`、`/compare/[comparisonSlug]`、`/matches`、`/deals`、`/search`、`/scene/[slug]`、`/auth` 可访问 |
| F-3 | 兼容路由行为正确 | `/rankings` 的重定向行为符合当前实现；`/tools` 作为工具目录页正常工作 |
| F-4 | 首页承接 | 首页可承接搜索、筛选、分页和视图切换 |
| F-5 | 详情页 | 工具详情页可展示基础信息、评论摘要和相似工具 |
| F-6 | 认证页 | `/auth` 提供登录、注册、已登录状态和退出能力 |
| F-7 | 后台页 | `/admin`、`/admin/tools`、`/admin/reviews`、`/admin/rankings`、`/admin/match-plans` 前端页面存在并可在有权限时进入 |
| F-8 | 响应式 | 主要页面在桌面和移动端布局正常 |
| F-9 | 不报错 | 浏览器控制台不应出现明显运行时错误 |
| F-10 | 岗位/任务识别 | 首页或场景入口应让用户能快速判断自己属于哪个岗位或要解决哪个任务 |
| F-11 | 场景方案表达 | 页面不能只停留在工具卡片展示，应能表达任务步骤、工具组合或下一步行动建议 |

## 三、后端验收标准

| 编号 | 项目 | 验收说明 |

## 四、测试验收标准

| 编号 | 项目 | 验收说明 |
| --- | --- | --- |
| T-1 | Web 单测 | `npm run test:web` 可执行 |
| T-2 | API 测试 | `python -m pytest` 可执行 |
| T-3 | 前端 E2E | Playwright 用例覆盖 smoke、visual、navigation、auth |

## 五、产品方向验收口径

- 用户进入首页或场景入口后，应能快速找到与自己岗位或任务相关的入口
- 每个核心场景的目标描述应围绕“解决工作问题”，而不是只罗列工具名称
- 每个核心场景至少应包含以下内容目标：
  - 用户问题
  - 推荐工具
  - 推荐理由
  - 使用步骤
  - 提示词模板
  - 注意事项
  - 示例结果
- 页面体验不能只展示工具卡片，必须给出可执行的工作流方案或下一步路径
- 若对应能力尚未落地，应在文档中明确标注为“产品方向”或“待实现”，不能伪装成当前事实

## 六、当前不作为验收前提的内容

- 旧的 `Vite` 或 `React Router` 路由实现
- 浏览器侧 `mock API`
- “后台管理未落地”的旧口径
- “评论未实现”的旧口径
- 第三方 OAuth、支付、会员、个人中心

## 七、验收方式

1. 先看 `docs/current-implementation-baseline.md`
2. 再核对真实路由、接口和模型
3. 再核对产品方向文档是否清楚区分当前事实与规划能力
4. 最后运行前端与后端测试
